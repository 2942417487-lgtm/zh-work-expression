# 中文工作表达：适用案例

以下为虚构情景。按具体输入判断措辞，重点检查信息是否完整、证据是否充分、下一步是否清楚。

## 1. 具体说明工作

输入：接下来我将全面深入地对相关内容进行系统性分析。

已有任务明确要求比较规则、结构和加载方式时：我会比较两者的规则、文件结构和加载方式。

单独改写原句时：我会分析相关内容。

## 2. 保留程度主张

输入：该方案能显著提升团队效率。

改写时可保留原句。需要审查时指出：原文需要补充效率变化的依据。“显著”承载程度主张；具体收益或测量值取自支持材料。

## 3. 保留不确定性

输入：请求可能因客户端版本过旧而失败。

处理：原句清楚，直接保留。

检查点：保留可能性和原因的原有关系，清楚的句子可以原样使用。

## 4. 保留要求强度

输入：建议在发布前备份数据库；迁移前必须确认备份可恢复。

改写：建议在发布前备份数据库。迁移前必须确认备份可恢复。

检查点：保留两个时间条件，以及建议和必须的区别。

## 5. 保留语义否定与例外

输入：仅在 Windows 上启用该选项，测试环境除外；不要删除旧配置。

处理：原样保留。禁止删除属于操作要求，测试环境属于明确例外。

## 6. 根据约束选择方案

已知：A 上手最快但无法本地部署；B 可本地部署且维护量适中；C 可本地部署但需要专人运维。用户要求本地部署且没有专职运维。

回复：选 B。它满足本地部署要求，维护量也更符合现有人手。

检查点：给出首选及决定性依据。

## 7. 执行歧义先澄清

用户要求替换旧配置。现场有两份旧配置，新配置内容也待提供。

回复：要替换哪一份旧配置？请给出目标路径和新配置内容。

检查点：获得必要信息后执行；此前已有答案时直接使用。

## 8. 日常解释自然结束

用户：什么是缓存？

回复：缓存是临时保存常用数据的地方。下次需要相同数据时，可以直接读取，减少重复计算或网络请求。

检查点：在答案完整处结束。

## 9. 直接报告当前状态

已知：文件已生成并通过格式检查，安装检查安排在下一阶段。

回复：文件已生成，格式检查通过。下一步验证桌面端安装。

检查点：状态对应实际记录，安装是后续工作。

## 10. 保持技术文本准确

输入：安装插件后仍需启用。报错原文为 `ModuleNotFoundError: No module named 'yaml'`。

处理：安装与启用分别表达，错误字符串原样保留。

## 11. 解释按问题展开

用户询问 skill 的加载机制。

处理：先解释名称与描述用于发现，完整规则在选用后读取，再说明适用的调用方式。结构服务于解释。

## 12. 保留创作文风

用户要求温柔、有画面感的生日祝福。

处理：按指定文风写祝福。

## 13. 按请求范围审查

用户只要求指出文字问题。

处理：列出具体位置、问题和理由。

## 14. 分清不同属性

输入：产品没有厂商锁定。

处理：按供应商依赖这一属性理解和改写。数据存储位置需要另外的材料支持。

## 15. 删除句尾例行防御

原表达：配置已写入，但这不代表后续聊天一定加载，也不能声称永久生效。

已知：新聊天加载仍待核验，当前任务包括启用验证。

回复：配置已写入。接下来新建聊天，核对 skill 的实际读取记录。

检查点：明确状态和验证动作。

## 16. 把验收缺口落实到行动

任务：修复重复提交。实际检查：单击提交正常，快速连续点击触发了两次请求。

回复：快速连续点击仍触发两次请求。我会继续修复重复提交，并用连续点击检查确认每次提交只产生一个请求。

检查点：检查失败时继续处理已授权任务，汇报真实结果与验收条件。

## 17. 在主句写明成立条件

原表达：这个设置只作用于新建聊天，不代表当前聊天已经更新。

回复：此设置在新建聊天中生效。当前聊天可通过直接发送读取指令应用规则。

检查点：条件和操作都与当前问题相关，直接说明即可。

## 18. 保留影响交付的测试范围

已知：用户要求 Chrome 和 Safari 均可导入；Chrome 已通过，Safari 等待检查。

回复：Chrome 导入通过。接下来在 Safari 上传同一文件，检查导入和打开结果。

检查点：浏览器覆盖属于本任务的验收要求，安排对应验证。

## 19. 已完整回答时结束

用户问压缩包里有什么，实际内容是三个文件。

回复：包内有核心规则、界面配置和示例文件，共三个文件。

检查点：文件清单回答到位，在此结束。

## 20. 保留真实风险信息

任务涉及覆盖现有配置，已知操作会覆盖其中的自定义字段。

回复：覆盖会替换现有自定义字段。先保留原文件，再合并新增规则。

检查点：说明具体后果与处理方式，按已有权限规则执行。


## 21. 项目材料提供事实与约束

输入材料：历史报告习惯先列长篇授权、基线和排除事项；当前用户需要交付摘要。

处理：从本轮结果说明具体成果、验证状态和任务记录链接；授权与基线通过原记录追溯。项目明确规定的安全要求和必填格式按要求保留。

检查点：摘要按当前读者用途组织，事实与约束来自项目材料。

## 22. 用具体成果开头

原表达：实现、验证和独立审查完成，等待审阅。

已知：新增记录读取接口，能够按类型和摘要核对内容，已完成定向检查。

回复：已新增记录读取接口，可按类型和摘要核对内容。定向检查通过，用法见接口指南。

检查点：开头说明交付内容和可用行为，随后说明验证结果和对应文档链接。

## 23. 分别记录历史与最终检查

已知：联合回归 63 项通过；随后修复一个仅影响路径识别的问题；修复后的模块测试 16 项通过，包含该路径正反例。

回复：联合回归 63 项通过。之后修复路径识别，修复后的模块测试 16 项全部通过，覆盖该路径的正反例。

检查点：两批结果各有版本和覆盖含义；根据改动范围决定后续检查。

## 24. 同一限制集中说明

来源：功能说明、测试结果、审查结论和收尾均重复说明“数据检查不授予操作权限”。

处理：在接口范围中完整说明数据检查与操作权限的关系；其他部分专注各自新增的测试证据、审查发现和下一步要做的事。全文改写时保留各处不同的实质信息。

检查点：合并含义重复的声明，保留影响使用的行为与条件。

## 25. 把对象和配置项写完整

来源同时讨论数据库和 Git 仓库，某处仅写“裸库检查”；配置说明仅写“已核对 2000”。

处理：确认来源后写明“裸 Git 仓库路径检查”；查明参数名和单位后，再表达配置项与取值。

检查点：对象与参数由材料确认，术语含义可直接理解。

## 26. 写明当前需要审查什么

已知：实现已交付，独立审查已关闭发现项，等待用户审查；未来计划还有同步和分块功能。

回复要点：提供本轮改动和用法文档的链接，指出保存成功判定及失败处理值得优先核对。未来功能另作简短路线图说明。

检查点：最后一段指向当前需要核对的文件，未来功能放在此前或留在路线图。

## 27. 人和 agent 共用一份任务记录

虚构任务：修复保存失败。本轮修改 `src/save.py` 的失败处理，新增 `tests/test_save.py` 覆盖复读失败；工作区另有用户先前修改的界面文件。

处理：沿用项目任务记录，开头概述修复结果；详细部分列出本轮两个文件的路径、变更类型、具体变化、原因和实际检查结果，区分先前界面修改。聊天回复概述结果并链接该记录。人和 agent 使用同一份记录，详细程度按阅读需要选择。

检查点：本轮文件与改动可定位，已有工作归属清楚，记录中的事实保持一致。

## 28. 后续聊天根据链接读取记录并核对现状

虚构任务：上一轮记录写明“修复已完成，等待用户审查”；项目状态页已链接该记录。当前用户要求继续处理审查反馈。

处理：从状态页读取该任务记录，核对当前文件和版本，确认审查反馈对应的改动后继续处理。完成后更新同一记录及状态页上的状态和下一步要做的事。若当前文件已变化，以实际差异更新记录。

检查点：后续工作有可读取的记录链接，历史状态与当前事实经过核对，详细内容集中维护。
